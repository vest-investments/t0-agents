
## Phase 1 Guide: Tools Adapter (FastMCP → TensorZero)

### 1. The format TensorZero expects for `additional_tools`

TensorZero accepts dynamic tools at inference time via the `additional_tools` field. Each **function tool** is an object with this exact structure:

```python
{
    "name": "...",          # string, required
    "description": "...",   # string, required
    "parameters": { ... },  # object (JSON Schema), required
    "strict": False          # boolean, optional, defaults to False
}
```

**Critical detail for F1.2 and F1.6:** In the native TensorZero API (`POST /inference`), `description` is **required**. The documentation states verbatim:

> * `name` (string, required): The name of the tool
> * `description` (string, required): A description of what the tool does
> * `parameters` (object, required): A JSON Schema defining the tool's parameters
> * `strict` (boolean, optional): Whether to enforce strict schema validation (defaults to `false`)

This means that if FastMCP returns `description=None`, your adapter **must** convert it to `""` (empty string) before sending it to TensorZero, or TensorZero will reject the tool.

(source: `gateway-api-reference.md` > "API Reference: Inference" > `additional_tools` > "Function Tools", original URL: https://www.tensorzero.com/docs/gateway/api-reference/inference.md)

### 2. The official MCP → TensorZero example (reference code)

TensorZero has an official MCP integration example. Tool conversion is done as follows:

```python
# Load the tools from the MCP server
mcp_tools = await session.list_tools()
mcp_tools = [tool.model_dump() for tool in mcp_tools.tools]

# Convert MCP tool format to TensorZero tool format
t0_tools = [
    {
        "name": tool["name"],
        "description": tool["description"],
        "parameters": tool["inputSchema"],
    }
    for tool in mcp_tools
]
```

The mapping is:

| MCP (via `model_dump()`) | TensorZero `additional_tools` |
|---|---|
| `tool["name"]` | `"name"` |
| `tool["description"]` | `"description"` |
| `tool["inputSchema"]` | `"parameters"` |

Note that **`inputSchema`** on the MCP side maps to **`parameters`** on the TensorZero side. The content of `parameters` must be a valid JSON Schema (not a file path, unlike static configuration in `tensorzero.toml`).

(source: `examples/mcp-model-context-protocol/main.py`)

---

### 3. How tools are passed when making an inference request

Tools are passed in the `additional_tools` field of the `POST /inference` request:

```python
response = await t0.inference(
    function_name="clickhouse_copilot",
    episode_id=episode_id,
    input={
        "messages": messages,
    },
    additional_tools=t0_tools,
)
```

**Important note:** The documentation recommends defining tools in the static configuration file when possible. Dynamic tools should only be used when the use case requires it (as is the case with MCP):

> You should prefer to define tools in the configuration file if possible. Only use this field if dynamic tool use is necessary for your use case.

(source: `gateway-guides.md` > "Defining tools dynamically at inference time")

---

### 4. Minimum required `tensorzero.toml` configuration

The function definition in the configuration file **does not need** to declare static tools if you intend to pass them dynamically. The official example uses this minimal config:

```toml
[functions.clickhouse_copilot]
type = "chat"

[functions.clickhouse_copilot.variants.baseline]
type = "chat_completion"
model = "openai::gpt-4.1-mini-2025-04-14"
system_template = "functions/clickhouse_copilot/baseline/system.txt"
```

There is no `tools = [...]` or `tool_choice` in the static config. Both are controlled at runtime.

(source: `examples/mcp-model-context-protocol/config/tensorzero.toml`)

### 5. `tool_choice` for F1.4

To force the LLM to always return a `ToolCall` (item F1.4), use `tool_choice="required"` in the inference request. The supported strategies are:

```
"none"                          → Do not use tools
"auto"                          → The model decides (default when tools are present)
"required"                      → The model MUST use a tool
{ "specific": "tool_name" }     → Force a specific tool
```

The default is `"auto"` when tools are present and `"none"` when they are not.

If you use the **OpenAI-compatible API** (`POST /openai/v1/chat/completions`), the `tool_choice` syntax is:

```
"none"
"auto"
"required"
{"type": "function", "function": {"name": "my_function"}}
```

(source: `gateway-api-reference.md` > `tool_choice`, and `gateway-configuration-reference.md` > `tool_choice`)

### 6. Response structure: how a `ToolCall` is received

When the LLM decides to call a tool, the response contains content blocks of type `tool_call` with the following fields:

```json
{
    "type": "tool_call",
    "id": "...",
    "name": "validated_tool_name (or null if invalid)",
    "raw_name": "name generated by the model",
    "arguments": { ... },
    "raw_arguments": "original string from the model"
}
```

Key fields:

- `name` / `arguments`: values **validated** by TensorZero (may be `null` if validation fails).
- `raw_name` / `raw_arguments`: raw values generated by the model (always present).

In the Python SDK, `isinstance(content_block, ToolCall)` is used to detect them:

```python
for content_block in response.content:
    if isinstance(content_block, Text):
        print(content_block.text)
    elif isinstance(content_block, ToolCall):
        print(f"Tool: {content_block.raw_name}")
        print(content_block.raw_arguments)
```

(source: `gateway-api-reference.md` > Response > Chat Function > `content`, and `examples/mcp-model-context-protocol/main.py`)

### 7. The multi-turn flow with tool results

After executing the tool, the result is returned to TensorZero as a `user` message with content blocks of type `tool_result`:

```python
t0_tool_result = ToolResult(
    name=content_block.name,
    result=t0_tool_result_text,  # string with the result
    id=content_block.id,         # must match the id of the tool_call
)

user_message = Message(
    role="user",
    content=tool_results,  # list of ToolResult
)
messages.append(user_message)
```

The `tool_result` content block requires:

- `id`: must match the `id` of the original `tool_call`.
- `name`: name of the tool.
- `result`: string with the result.

(source: `gateway-api-reference.md` > content blocks > `tool_result`, and `examples/mcp-model-context-protocol/main.py`)

### 8. On `parameters` and JSON Schema (F1.5)

The `parameters` field must contain a valid **JSON Schema**. The documentation example for a static tool shows this format:

```json
{
    "$schema": "http://json-schema.org/draft-07/schema#",
    "type": "object",
    "description": "Get the current temperature for a given location.",
    "properties": {
        "location": {
            "type": "string",
            "description": "The location to get the temperature for"
        },
        "units": {
            "type": "string",
            "description": "The units (must be 'fahrenheit' or 'celsius')",
            "enum": ["fahrenheit", "celsius"]
        }
    },
    "required": ["location"],
    "additionalProperties": false
}
```

When FastMCP generates schemas from Pydantic models, the resulting `inputSchema` should already be a valid JSON Schema. Your adapter simply passes `tool["inputSchema"]` as `parameters`. TensorZero forwards it as-is to the model provider.

If you enable `strict: true` on a tool, the provider (if supported, e.g. OpenAI) will use strict JSON generation (Structured Outputs). This improves quality, but not all providers support it; if they don't, the field is ignored.

(source: `gateway-guides.md` > JSON Schema example for `get_temperature`, and `gateway-configuration-reference.md` > `strict`)

### 9. OpenAI-compatible API (alternative)

If you prefer to use the OpenAI-compatible API instead of the native API, tools are passed in OpenAI standard format in the `tools` field:

```python
tools=[
    {
        "type": "function",
        "function": {
            "name": "get_temperature",
            "description": "Get the current temperature in a given location",
            "parameters": { ... }  # JSON Schema
        }
    }
]
```

Here `description` is **optional** (not required as in the native API).

(source: `gateway-api-reference.md` > API Reference: Inference (OpenAI Compatible) > `tools`)

### Mapping checklist for your adapter

| Item | What you need to verify on the TensorZero side |
|---|---|
| **F1.1** | That FastMCP objects have `.name`, `.description`, `.inputSchema` accessible (this is your FastMCP side) |
| **F1.2** | That your `list[mcp.types.Tool]` is converted to `list[dict]` with exact keys `name`, `description`, `parameters` |
| **F1.3** | That passing `additional_tools=t0_tools` in `t0.inference(...)` does not cause T0 to raise an error |
| **F1.4** | That with `tool_choice="required"`, the response always contains at least one content block with `type: "tool_call"` |
| **F1.5** | That schemas generated by Pydantic (`inputSchema`) are valid JSON Schemas accepted by T0 |
| **F1.6** | That tools with `description=None` are converted to `description=""` before being sent to T0 (because `description` is **required** in the native API) |

---

### Potential conflict to keep in mind

There is a difference between the two TensorZero APIs regarding `description`:

- **Native API** (`POST /inference`): `description` is **required**.
- **OpenAI-compatible API** (`POST /openai/v1/chat/completions`): `description` is **optional**.

If you decide to use the OpenAI-compatible API, handling `description=None` may not be an issue. But if you use the native API (as in the official MCP example), you must ensure it is always a string.

(source: `gateway-api-reference.md`, sections of both APIs)
